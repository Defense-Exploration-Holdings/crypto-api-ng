# Porting guide: how an algorithm gets into crypto-api-ng

MD5 (`src/hash/md5.zig`, `src/wasm/md.zig`, `packages/crypto-api/src/hasher/md5.mjs`) is the template. Copy its shape, change what the algorithm needs, and keep the rule of the v1 release: **same outputs, same `getState()` JSON, same behavior for every input crypto-api 0.8.5 accepts, bugs included.** Fixes are v2.

See also [abi.md](abi.md) for the wasm calling conventions and [test-harness.md](test-harness.md) for the parity tests.

## The idea in one paragraph

Each hasher class in the package **extends the verbatim 0.8.5 class** and overrides only the two methods that burn CPU, `process()` (compress full blocks) and `finalize()` (pad and compress the last block). The hasher's state stays the original plain object (`this.state = {message, length, hash}`), so `update()`, `reset()`, `getState()`, `setState()`, direct `.state` access, non-string input and wide characters are the original code, and there is no engine to switch and no state to translate. Before every wasm call the override checks that the state and the class are exactly what the wasm code models; if not, it calls `super.process()` / `super.finalize()` and the original does the work. Nothing about a hasher is kept in wasm memory: each call writes what it needs into one shared scratch region and reads the result back.

Why not hold the state in a per-hasher `Uint8Array` blob that is copied in and out (the first design we tried)? Measured on Node 22: `new Uint8Array(96)` costs about 900 ns, plain objects about 30 ns. With blobs, `new Md5()` took ~1 µs; with this design it takes ~30 ns. The blob design also needed a state mapping, a "demotion" switch to the legacy engine, and a `state` accessor. All of that goes away.

## Files for one algorithm

| File | Role |
|---|---|
| `src/hash/<algo>.zig` | Target-agnostic core: `State` (`extern struct`, fixed layout), `init`, `update`, `final`, `blocks`, plus `test` blocks. No wasm or OS code. Re-export from `src/root.zig`. |
| `src/wasm/<family>.zig` | wasm root for the family: `comptime { _ = @import("common.zig"); }` plus `export fn <algo>_*` wrappers. One module per family (`md`, `sha1`, `sha256`, `sha512`, ...). Add the family name to `families` in `build.zig`; `zig build js` then embeds it as `packages/crypto-api/wasm/<family>.mjs`. |
| `packages/crypto-api/legacy/hasher/<algo>.mjs` | The original file, import specifiers only rewritten (generated by `scripts/vendor-legacy.mjs`). Its base-class imports point at `../../src/hasher/*.mjs`, so there is a single `Hasher32le`, and `new Md5() instanceof Hasher32le` holds. |
| `packages/crypto-api/src/hasher/<algo>.mjs` | The facade (first line `// crypto-api-ng:facade`, so the vendoring script never overwrites it). Same default export and path as 0.8.5. |
| `test/vectors/<algo>.json`, `test/<algo>.test.js` | Vectors and the differential test against the legacy class. |

## Zig core

- `State` is an `extern struct` with a documented layout and a `comptime` size/offset assertion. JS writes fields at these offsets, so changing the layout means bumping `runtime.abi_version`.
- Constants are literals. Cross-check them in a Zig test (MD5 pins `T` against `std.math.sin`, the only place a float appears) and against `std.crypto` where it has the algorithm. `std.crypto` is an oracle for default parameters only: it has no `rounds`, and it does not keep the original's 32-bit length bug.
- `update`/`final` should mutate the state exactly like the original `update`/`finalize`. For MD5 that means `final` leaves the buffer drained, the hash words advanced and `length` untouched, so a second `finalize()` or an `update()` after `finalize()` gives what 0.8.5 gives (tests pin real values captured from 0.8.5).
- Reproduce quirks in a function of their own with a doc comment (`md5.lengthField`: the original's length bytes come from `ToInt32(length)` with arithmetic shifts, which is only the RFC length below 2^31 bytes) and test it against values captured from the original, including values past the quirk's threshold.
- `blocks(hash, data)` compresses whole blocks and touches nothing else. The facade uses it because buffering and counting stay in JS.

## wasm export shape

```
<algo>_state_size() -> u32
<algo>_init(state)
<algo>_update(state, data, len)
<algo>_blocks(state, data, len)      // len % block == 0; hash words only
<algo>_final(state, out)
```

`state`, `data` and `out` are absolute addresses inside the fixed scratch region exported by `common.zig` (`scratch_ptr()`, `scratch_len()`): state at +0, output at +128, input chunk at +256 (capacity `scratch_len() - 256`, 64 KiB). There is no `alloc`/`free`. Memory is fixed at 2 pages (`max_memory == initial_memory`), so it can never grow and the facade caches one `Uint8Array` over it.

## The facade

Copy `md5.mjs` and change the algorithm-specific parts. The parts that carry the guarantees:

1. `class X extends LegacyX`: never re-implement `update`, `reset`, `getState`, `setState`. Inherit them.
2. Override `process()`:
   - `const state = this.state`; if it is not an object, or `state.message` is not a string, `return super.process()`.
   - If `message.length < blockSizeInBytes`, return (that is what the original does).
   - Delegate to `super.process()` unless `this.processBlock === ORIGINAL_BLOCK` (a subclass or instance patch must be honored), the hash words are integers of magnitude at most 2^52 (`hashOk`; beyond that the original's double sum `word + a` rounds), and the runtime loaded.
   - Copy the block-aligned part of the message into scratch in chunks of the scratch capacity, OR-ing the code units. If any is above 0xFF, write back what has been consumed so far (always whole blocks), set `state.message = message.substr(pos)` and `return super.process()`. The original then handles the rest, garbage output included.
   - Write the hash words back **in place** (`state.hash[i] = ...`, as the original does) and set `state.message = message.substr(total)`.
3. Override `finalize()` only if the padding and last block are worth accelerating. Guard on everything it relies on (`process`, `processBlock`, `addLengthBits`, `addPaddingISO7816`, `getStateHash` not overridden; message short and narrow; hash and length safe integers), fill the scratch `State`, call `<algo>_final`, copy the new hash words back, set `state.message = ''`, and build the digest with `String.fromCharCode`. Nothing in `this` may be touched before the guards pass.
4. Load wasm lazily (first call), remember a failure, and treat it as "delegate everything". `instantiate()` in `src/wasm/family.mjs` returns `null` instead of throwing.
5. Options: normalize them with the inherited constructor and `reset()` as before, and take the wasm path only when they are inside the envelope the original's own options allow (otherwise `super.process()`).
6. Export `_internal` for tests (wasm call counter, runtime handle, a way to simulate "no WebAssembly"). It is not public API.

Known, deliberate non-parity of the MD5 facade: `blockUnits` (an `@private` scratch array in `Hasher32le`) is not filled on the wasm path. Nothing else differs; `Object.keys(hasher)`, `JSON.stringify(hasher)`, `hasher.state` and the live-reference behavior of `setState()` are identical.

## Sharing the facade glue: the 32-bit big-endian family

SHA-0, SHA-1, SHA-224/256 and SM3 differ from each other only in numbers (hash words, `State` offsets, the option rules), so their `process()`/`finalize()` logic lives once in `packages/crypto-api/src/wasm/be32.mjs` and each facade is about 30 lines:

```js
const accel = createAccelerator({family, name: 'sha1', legacy: LegacySha1, words: 5,
  roundsOff: 20, lengthOff: 24, bufferedOff: 32, bufOff: 40,
  rounds: (o) => roundsIn(o, 80), outBytes: () => 20, facade: () => Sha1});
class Sha1 extends LegacySha1 {
  constructor(options) { super(options); }   // keeps Sha1.length === 1
  process() { if (!accel.process(this)) super.process(); }
  finalize() { const r = accel.finalize(this); return r === null ? super.finalize() : r; }
}
```

The guards are the ones of the MD5 facade (state shape, `processBlock` and the other internals not overridden, `blockSizeInBytes` 64, wide characters, a missing runtime) plus option checks done **at call time**, because the original reads `this.options.rounds` and `this.options.length` on every block: `rounds` must be an integer in 1..max, and `finalize()` needs a `length` the wasm output size supports (SHA-224/256: 224 or 256, SM3: 256). `process()` does not look at `length`, which only picks the IV in the original's `reset()` and the output size in `finalize()`. A little-endian family (MD4, HAS-160, RIPEMD) would add a sibling `le32.mjs`; do not bend `be32.mjs` for it.

### 128-byte blocks: SHA-384, SHA-512, SHA-512/224, SHA-512/256

`Sha512` in 0.8.5 is still a `Hasher32be` (32-bit units, `blockSize` 32 units = 128 bytes, sixteen int32 hash words as hi/lo pairs), so it uses the same glue with two extra parameters of `createAccelerator`: `block: 128`, and `outOff: 256`. Its Zig `State` is 216 bytes (the 128-byte buffered tail alone fills the slot), more than the 128-byte state slot of the scratch region, so the digest is written to the input offset instead of `OUT_OFF`; `sha512_final` does not read the input region. What is specific to this family:

- One compression serves all four algorithms. The IV is whatever is in `state.hash` (the original's `reset()` makes it), and `length` only decides how many digest words `finalize()` returns, `(length / 32) | 0` of them. Wasm therefore serves any integer `length` from 32 to 512 for `finalize()`, including the SHA-512/t IVs the original derives for other t. This is wider than the envelope the original documents and costs nothing: there is no length-dependent code in wasm.
- `rounds` counts 32-bit half-steps: the original loops `i = 0, 2, ... < rounds`, so `ceil(rounds / 2)` steps (159 equals 160, 1 equals 2). Wasm serves integers 1..160.
- The length field is 16 bytes, eight zero bytes then the same 32-bit-bug field as the other hashers (`be32.lengthField`); padding goes to offset 112, or 240 when the tail is 112 bytes or more.
- `reset()` is overridden for `length` 224 and 256 only: the original derives their IV with a full SHA-512 of `"SHA-512/224"` (resp. 256) on every construction, which cost more than hashing a short message. The facade writes the FIPS 180-4 constants instead (a Zig test derives them with the same procedure and compares). Every other length, and any subclass that patched the original `reset`, still runs the original code. The state it leaves is identical, key order included.

### Whirlpool: three variants, one module

`Whirlpool` is a `Hasher32be` with 64-byte blocks, so it uses the same glue as SHA-512 (`outOff: 256`, because its `State` is 152 bytes). What is specific to it:

- **Variants.** Whirlpool-0 (`type: '0'`), Whirlpool-T (`type: 't'`) and Whirlpool differ only in tables. The Zig core derives them at compile time exactly like the original's `calculateSBOX()`/`calculateRC()` (Whirlpool-0's S-box stays a literal), and keeps only the 256-entry `C[0]` column (2 KB per variant); the other seven columns are rotations by whole bytes. One module exports three sets of the same functions (`whirlpool_*`, `whirlpool0_*`, `whirlpoolt_*`, made with `@export` from one comptime function), and the facade owns three accelerators on one shared instance. A Zig test pins FNV-1a fingerprints of all of `C[0..8]` and `RC`, taken from the original's own tables, for each variant.
- **The facade does not read `options.type`.** The original's constructor turns it into a pair of module-private tables (`this.C`, `this.RC`) with a `switch` that accepts `0`, `'0'`, `'t'`, `true`, `'x'`, ... in its own way (the number `0` becomes `''` first and selects plain Whirlpool). The facade finds the three tables by constructing one original hasher per type on first use and compares by identity, so whatever the original selects, wasm serves. Tables an instance or subclass replaced with something else are unknown and run the original.
- **Rounds** 1..10 run in wasm. 11 and above read `RC[r*2]` past the end of the original's table (`undefined`), so they stay on the original.
- **Padding** differs from the `be32` default: a tail shorter than 32 bytes is padded to offset 56, any other to 120, then the usual 8-byte length field (the original's field is 8 bytes, not the specification's 32; for messages below 2^31 bytes the bytes are the same). `whirlpool.zig` has its own `finalTail`.
- Hash words only go through XOR and shifts in the original, so any integer word is exact; the shared `hashOk` bound (|word| < 2^52) is harmless here.

### MD2: byte-oriented, its own module

`Md2` is a `Hasher8`: 16-byte blocks, no length field (it never looks at `state.length`, so the length bug does not exist here), and a state that is **two arrays**, `state.hash` (48 numbers) and `state.checksum` (16 numbers). The glue in `be32.mjs` does not fit (words, length, ISO padding), so `md2.mjs` is a standalone facade in the shape of `md5.mjs`:

- A pristine state holds `new Array(48)` and `new Array(16)`: holes in memory, `null` after `getState()`, and the original reads both as 0. The facade accepts `undefined`, `null` and integers 0..255 in either array, sends them to wasm as bytes and writes **every** entry back, in place, afterwards. That is exactly the original's end state, because with `rounds >= 1` each block rewrites all 48 hash bytes and all 16 checksum bytes. Anything else (fractions, strings, values above 255 that wide characters leave behind, a wrong length) runs the original.
- If a wide character shows up after some blocks already ran in wasm, the consumed blocks' hash and checksum are written back before the original takes over; if it shows up in the first chunk nothing is written, so a state with holes is left untouched.
- `finalize()` is two compressions (the PKCS#7-padded tail, then the checksum as one more block) and leaves the checksum advanced by that second block; wasm does both and the facade writes both arrays back. `rounds` 1..2^32-1 is served (the round counter only matters through its low byte).
- MD2 is a serial chain (each step's S-box index is the previous step's result), so wasm gains little: about 1.1 to 1.3x end to end in the measurements below. It is its own family module `md2.wasm` (1.4 KB) instead of joining `md`, so the MD4 port does not collide with it.

Things the pattern taught that apply to every family:

- Give the facade an explicit `constructor(options) { super(options); }`. An implicit derived constructor has `length` 0 and the harness's shape test checks `Class.length`.
- The original `finalize()` calls `this.process()`, so a facade whose `finalize()` falls back still runs the final block in wasm through its own `process()` when it can. Expect that when counting wasm calls in tests.
- Families whose algorithms share a module (`sha1` serves SHA-0 and SHA-1) share one instance through `createFamily` in a small `src/wasm/<family>-family.mjs`.
- Wasm exports that read `rounds` from the State validate it and return `Status.invalid_argument`, so a bad State cannot write out of bounds in a `small` build, where asserts are compiled out.
- Known non-parity, same as `blockUnits`: the `@private` scratch array `this.W` (the message schedule) stays empty on the wasm path, so `JSON.stringify(hasher)` shows an unfilled `W`. `getState()` is unaffected.

## Sharing the plumbing: `le32` (MD4, HAS-160, RIPEMD)

Every `Hasher32le` algorithm pads and counts the same way, so MD4, HAS-160 and RIPEMD do not copy `md5.mjs` and `md5.zig`. They use two shared files and keep only what is algorithm-specific:

- Zig: `src/hash/le32.zig` provides `Hasher(words, iv, compress)`, which gives an algorithm its `State`, `init`, `update`, `blocks` and `final` (padding, the 32-bit length-field quirk, the state left after `finalize()`). The algorithm file (`md4.zig`, `has160.zig`, `ripemd.zig`) is the compression function, its constants and tests. `src/wasm/le32_exports.zig` generates the five exports from that type, so a family root is a few lines.
- JS: `packages/crypto-api/src/wasm/le32.mjs` does the scratch-region copying for `process()` and `finalize()` (`accelProcess`, `accelFinalize`) and the lazy, failure-remembering `Engine`. The facade file (`md4.mjs`, `has160.mjs`, `ripemd.mjs`) is ~80 lines: extend the original class, decide when wasm is allowed, call the helper, else `super`.
- Tests: `test/support/le32-suite.js` is the "Tests every port needs" checklist below as a function of (facade, original class, options). Each algorithm's test file calls it once per option set and adds its own cases.

Use these for any other 32-bit little-endian, 64-byte-block hasher. SHA families (big-endian words) and the 128-byte-block ones will want their own equivalent.

Things the three ports turned up that the MD5 text above does not say:

- **Guard hash words to |w| <= 2^52, not "safe integer".** The original computes `(word + x) | 0` in doubles. Up to 2^52 the sum is exact, so it equals wasm's int32 add; near 2^53 the sum rounds and the two disagree. (`md5.mjs`'s `hashOk` accepts all safe integers and has this bug; see the PR notes.)
- **Mirror how the original stores the result.** MD4 assigns a fresh `state.hash` array after every block (the facade does too, `replace`), the others write into the existing array. Only touch `state.hash` when at least one block really was processed: HAS-160's initial words are unsigned until then, and `getState()` shows it.
- **Per-instance function choice.** RIPEMD's `reset()` stores `processBlock128/160/256/320` on the instance. The facade picks the wasm variant from which function the instance holds, never from `options.length`, so `length: 100`, `'256'` or a hand-assigned `processBlock` do exactly what 0.8.5 does. A subclass `processBlock` is shadowed by that instance property in the original too.
- **Options read at call time.** HAS-160 reads `options.rounds` in `processBlock`, so the facade reads it on every `process()`/`finalize()` and sends integers 0..80 to wasm in `State.param`; everything else (strings, fractions, > 80) is original code. `rounds: Infinity` makes the original loop forever, so tests never probe it.
- **Constructor arity.** A derived class without a constructor has `length` 0. The original `Has160` and `Ripemd` take `(options)`, so their facades spell out `constructor(options) { super(options); }` (the harness checks `T.length`).
- **Guard `blockSizeInBytes`.** `process()` reads the instance property, so the facade checks it is 64. (A value of 0 makes the original loop forever; not probed.)
- Not filled on the wasm path: `blockUnits` (all of them) and HAS-160's `W`, both private scratch arrays. Static helpers patched on the exported class (`Md4.FF`, `Ripemd.F`, ...) are not seen by the legacy engine, which calls its own class.

Measured (Node 22, cloud sandbox, `--release=small`, one `new X(); update(s); finalize()`; ratios only, the machine is noisy):

| Algorithm | 0 B | 1 KiB | 64 KiB | 1 MiB | wasm compress alone | module |
|---|---|---|---|---|---|---|
| MD4 | 3.4x | 4.1x | 4.3x | 3.2x | ~660 MB/s | `md.wasm` 5.1 KB (with MD5) |
| HAS-160 | 1.9x | 2.4x | 2.5x | 2.3x | ~300 MB/s | `has160.wasm` 2.2 KB |
| RIPEMD-160 | 1.8x | 1.8x | 1.5x | 1.6x | ~240 MB/s | `ripemd.wasm` 8.9 KB (all four) |
| RIPEMD-320 | 2.2x | 1.5x | 1.5x | 1.4x | ~165 MB/s | same module |

RIPEMD and HAS-160 gain less than MD4/MD5 because their original JS is already close to what a plain loop does and the wasm compression is only 2 to 3x faster; the string-to-bytes copy (~440 MB/s) is the shared ceiling. The compression loops use a comptime round index (`inline for` over rounds, plain `for` inside) because that gave +15 to +40 percent over a runtime `i / 16` switch at about +2 KB; full unrolling (`--release=fast`) costs 5x the size (ripemd 52 KB) for little end-to-end gain.

## Snefru: a standalone shape (block size depends on an option)

Snefru is `Hasher32be`, but nothing in the SHA glue fits: the block is `16 - words` words (`words` = `options.length / 32`, 1..15), the padding is zeros plus the 8-byte length of `addLengthBits`, `rounds` is read at every block, and 16 S-boxes (16 KiB) are generated when the module loads. So it has its own files instead of the shared plumbing, and is a good example of what to do when a family does not fit.

- **Zig core** (`src/hash/snefru.zig`). One `State` for every digest size (128 bytes, fixed layout, see abi.md), with `words`, `rounds` and `buffered` as `u8` fields. Because they are indices, every export validates them and returns a `Status`. The S-boxes are built at comptime by `Digits` and `sbox`, a direct transcription of `getRandomDigit`/`getRandomNumber`/`generateSbox` with the same running position in the RAND table across all 16 boxes. The table itself is `src/hash/snefru_rand.zig`, generated textually from the vendored original by `scripts/gen-snefru-rand.mjs`, so the Zig and JS sides cannot drift (`test/compat/vendor.test.js` runs its `--check`). Zig tests compare an FNV-1a of each of the 16 generated boxes, their first and last words, and that every byte column is a permutation, against what the original generates (`node scripts/gen-snefru-rand.mjs --dump`). Comptime generation costs about 2 s of compile time.
- **Compression loop.** The 16 steps and the 16 rotations are `inline for` over comptime indices: with runtime indices the working array stays in memory and compress ran at 20 MB/s, unrolled it keeps the words in registers and runs at 33 to 43 MB/s (the original JS: 10 to 17 MB/s). The loop is a serial dependency chain, so there is little more to gain without changing the algorithm.
- **Block and digest size.** `process()` serves any digest of 1..15 words, as long as `this.blockSizeInBytes === 4 * (16 - state.hash.length)`; the chunk copied into scratch is the largest multiple of the block size that fits in 64 KiB (the other families can use 64 KiB as is). `finalize()` serves 1..14 words: with 15 words the block is 4 bytes, so the original's `addPaddingZero(blockSize - 8)` throws RangeError after mutating the message, and that is left to the original code (a test pins it). A digest of 0 words (`length` below 32) has no output and is original code too.
- **Hash words.** The original only xors them (`^`, `| 0`), which is ToInt32 for any Number, the same conversion an `Int32Array` store performs. So, unlike the add-based families, no word magnitude limit is needed: fractions, 2^60, NaN and the like are computed in wasm identically (a test checks). Words that are not `typeof 'number'` are original code.
- **Options.** `rounds` is checked at every call; integers 1..8 run in wasm. `0`, negatives, fractions, strings and 9 and up are original code (9 and up throw TypeError in the original; the state after the failed block is compared in a test). `options.length` only matters in `reset()`, which is the original code, so the facade never looks at it.
- **Deliberate difference 1 (see the package README).** `length` of 512 and up makes the block size 0 or negative, and `process()` loops forever in 0.8.5. The facade throws `RangeError` in `process()` when it can tell the original would loop (block size <= 0, original `processBlock`, numeric `rounds` with `rounds << 1 <= 16`, so no TypeError first). Everything else about such an instance (constructing, `getState()`, `reset()`, and `finalize()` with an empty message, which already throws RangeError in the original) is unchanged. The `todo` markers in `test/compat/divergences.test.js` are gone.
- **Import cost.** The legacy module still builds its S-boxes at load (a few ms), because the legacy file is verbatim. v2 drops that.
- Known non-parity, same class as the other families: the scratch arrays `W` and `blockUnits` are not filled on the wasm path.

Measured (Node 22, cloud sandbox, `--release=small`, one `new Snefru(o); update(s); finalize()`, original vs facade; ratios only): 128/8 2.0x (0 B), 2.7x (64 B), 2.5x (1 KiB), 2.5x (64 KiB), 3.2x (1 MiB); 256/4 2.3x to 3.2x; 256/8 2.4x to 3.7x; 128/2 2.5x to 3.5x. `snefru.wasm` is 20 KB (16 KB of it the S-boxes).

## Tests every port needs

- Zig: official vectors, `std.crypto` cross-check at every length 0..300 with random update splits, quirk functions against values captured from 0.8.5.
- JS differential (`test/<algo>.test.js`), comparing the facade with the legacy class through digest, `JSON.stringify(getState())` after every call, and thrown errors:
  - random messages split across random `update()` calls, including block-boundary lengths; `FUZZ_ITERS` raises the count (default 200, release gate 100000);
  - `finalize()` twice, `update()` after `finalize()`;
  - inputs spanning several scratch chunks, and exact chunk multiples;
  - wide characters (first block, later block, exactly at a chunk boundary, only in the unprocessed tail);
  - non-string input (typed arrays, numbers, arrays, `null`, `undefined`, `Symbol`);
  - odd states through `setState()` (reordered keys, missing fields, non-integer or oversized words, `null`);
  - the length quirk at and beyond its threshold;
  - subclass and instance overrides of every internal the facade replaces;
  - no WebAssembly (global missing, `WebAssembly.Module` throws), with the failure remembered;
  - memory never grows after 20k hashers;
  - `Hmac` over the facade.
- Run `zig build check` in debug, and in `--release=small|fast|safe` before merging.

## Measurements (MD5, Node 22 in the cloud sandbox, so use the ratios, not the absolute numbers)

Facade vs the original class on one `new Md5(); update(s); finalize()` round, wasm built `--release=small`:

| Input | original | facade | speedup |
|---|---|---|---|
| 0 B | 2.4 µs | 0.55 µs | 4.4x |
| 64 B | 4.3 µs | 0.72 µs | 5.9x |
| 1 KiB | 26 µs | 4.2 µs | 6.2x |
| 64 KiB | 1.49 ms | 0.27 ms | 5.4x |
| 1 MiB, one update | 23.7 ms | 4.6 ms | 5.2x |
| 1 MiB in 4 KiB updates | 27 ms | 4.8 ms | 5.7x |

The wasm compression alone runs at about 490 MB/s (`small`) to 620 MB/s (`fast`). The facade tops out near 240 MB/s because copying the binary string into wasm memory with `charCodeAt` (about 440 MB/s here) costs as much as the hashing. That copy is the next thing to optimize (for example `TextEncoder.encodeInto` for pure-ASCII chunks, or a `Buffer` latin1 fast path on Node); the v2 bytes-in API removes it.

Decisions taken from the measurements:

- **Per-family modules, built `--release=small`.** `md.wasm` is 3.0 KB with `small`, 25 KB with `fast` (full unrolling), 56 KB with `safe`, 650 KB in debug. `fast` hashes 20 to 25 percent quicker in isolation and makes no visible difference end to end. A single combined module cannot be compared yet with one algorithm in it; re-measure when the SHA families land. The scaffold's `crypto-api.wasm` (general runtime, 1.1 KB) stays for the loader tests.
- **Copy-in skip is not worth it.** Copying the 96-byte state in and out costs about 50 to 70 ns per call, and the facade no longer copies state at all: the hash words and tail are written straight into scratch.
- **Small appends cost nothing in wasm.** `update()` below one block never calls wasm (`process()` returns early), so `Hmac`'s 64 one-byte updates are plain string work.

### MD2 and Whirlpool (Node 22 in the cloud sandbox, `--release=small`, ratios only)

One `new` + `update` + `finalize` round, original vs facade:

| Input | MD2 | Whirlpool | Whirlpool-0 |
